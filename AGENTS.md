# Как работать с TinyDB: люди и AI-агенты

Канонический текст для инженера и для любого агента. Cursor дополнительно
подмешивает те же ограничения из `.cursor/rules/*.mdc` (формат Project Rules:
YAML-frontmatter, `alwaysApply` / `globs` / `description`). Файл `.cursorrules`
не используем: для Cursor это устаревший формат.

Снимок кода — TinyDB **4.9.0** с <https://github.com/msiemens/tinydb>.
Это учебная копия, а не форк, в который нужно отправлять изменения автору.
Вверх по течению проект в режиме сопровождения: багфиксы и маленькие
вклады уместны, новый архитектурный слой — нет.

## Проект для новичка

TinyDB — документная база на чистом Python, без зависимостей и без сервера.
Документ — это `dict`. Данные по умолчанию лежат в одном JSON-файле.
Библиотека рассчитана на маленькие программы, которым тяжело тащить SQL
или отдельный сервер.

Три обычных сценария:

1. Запомнить и найти документы в таблице по умолчанию.

```python
from tinydb import TinyDB, Query

db = TinyDB("db.json")
db.insert({"name": "Ada", "age": 36})
User = Query()
db.search(User.age >= 30)
db.close()
```

2. Разложить данные по именованным таблицам: `db.table("orders")`.
   Пока таблицу не попросили, чтение и запись идут в `_default`.
   `TinyDB` проксирует неизвестные атрибуты в эту таблицу
   (`insert`, `search`, `get`, `len`, итерация).

3. Подменить хранилище или обернуть его middleware.

```python
from tinydb import TinyDB
from tinydb.storages import JSONStorage, MemoryStorage
from tinydb.middlewares import CachingMiddleware

db = TinyDB(storage=MemoryStorage)  # без файла
db = TinyDB("db.json", storage=CachingMiddleware(JSONStorage))
```

Из корня пакета наружу отдаются только `TinyDB`, `Query`, `where`,
`Storage`, `JSONStorage`. Middleware и операции импортируют из своих модулей.

Как запустить проверки локально (нужен Python 3.10+):

```text
uv sync --group dev
uv run py.test -v --cov=tinydb
```

Отдельной extra `[dev]` в `pyproject.toml` нет: зависимости для разработки
лежат в `[dependency-groups]`. `pytest.ini` уже включает `--cov`, поэтому
голый `pytest` без `pytest-cov` падает на опциях, а не на тестах.
Покрытие — цель проекта (вверх по течению заявляют 100%). Новый ветвящийся
код без теста не готов.

Ручная проверка в интерпретаторе: `TinyDB(storage=MemoryStorage)`, чтобы
не создавать `db.json` в дереве исходников.

## Модули и ответственность

| Путь | За что отвечает |
| --- | --- |
| `tinydb/__init__.py` | Публичный фасад и `__all__`. Новые символы сюда не добавлять без явной просьбы. |
| `tinydb/database.py` | Жизненный цикл хранилища, реестр таблиц, прокси к таблице `_default`, контекстный менеджер. |
| `tinydb/table.py` | CRUD, `Document`, кэш запросов, выдача `doc_id`. |
| `tinydb/queries.py` | `Query`, `where`, построение условий. |
| `tinydb/storages.py` | Контракт `Storage`, `JSONStorage`, `MemoryStorage`. |
| `tinydb/middlewares.py` | Цепочка middleware. Класс оборачивает storage, а не таблицу. |
| `tinydb/operations.py` | Функции для `Table.update`: `delete`, `add`, `subtract`, `set`, `increment`, `decrement`. Каждая возвращает callable от документа. |
| `tinydb/utils.py` | `LRUCache`, `FrozenDict`, `freeze`, `with_typehint`. |
| `tinydb/mypy_plugin.py` | Плагин типов. Не трогать, если задача не про типизацию. |
| `tinydb/version.py` | Строка `__version__`. Не менять, если релиз не просили. |
| `tests/` | Пиротесты. Фикстура `db` в `tests/conftest.py` гоняет один и тот же тест на `MemoryStorage` и `JSONStorage` и заранее кладёт три документа `{'int': 1, 'char': 'a'|'b'|'c'}`. |
| `docs/` | Sphinx. Менять только если задача про документацию или пользовательский контракт, который уже описан в `docs/`. |

Поток данных: `TinyDB` держит один `Storage`. `Storage.read()` / `write()`
видят всю базу сразу. Таблица не пишет «свою» часть файла в обход
`Table._update_table`.

## Термины

- **Document** — `dict` плюс `doc_id`. Идентификатор лежит на атрибуте
  `doc.doc_id`, а не в поле `_id` внутри словаря.
- **doc_id** — целое (`Table.document_id_class = int`). Первая запись
  получает `1`. В JSON ключи объектов — строки, поэтому на диске id
  хранится строкой и при чтении снова становится `int`.
- **Table** — именованный набор документов. Имя таблицы по умолчанию:
  `TinyDB.default_table_name = '_default'`.
- **Query / where** — условие. `where('age')` это короткий `Query`.
  Условия складываются через `&`, `|` и `~`. Пустой `Query()` нельзя
  вычислять: это `RuntimeError`.
- **Storage** — абстракция `read() -> dict | None`, `write(data)`,
  необязательный `close()`. `None` значит «хранилище пустое».
- **Middleware** — объект, который притворяется классом storage.
  `TinyDB` вызывает `storage(*args, **kwargs)`. У middleware `__call__`
  создаёт нижний storage и возвращает `self`.
- **Operation** — функция из `operations.py`, которую передают в
  `db.update(...)`. Она не трогает хранилище сама.

Модель на диске (её нельзя «улучшать» попутно):

```text
{
  "_default": {
    "1": {"name": "Ada"},
    "2": {"name": "Grace"}
  },
  "orders": { }
}
```

## Что нельзя менять, и почему

- Набор и смысл публичных методов `Table` / `TinyDB`: `insert`,
  `insert_multiple`, `all`, `search`, `get`, `contains`, `update`,
  `update_multiple`, `upsert`, `remove`, `truncate`, `count`,
  `clear_cache`. Это контракт пользователей и расширений.
- Имена в `__all__` корня пакета и поведение `Query` (`==`, `!=`,
  сравнения, `exists`, `matches`, `search`, `test`, `any`, `all`,
  `one_of`, `fragment`, `noop`, `map`). Смена семантики — мажорная
  версия по SemVer, её не делают в обычной задаче.
- Формат JSON и правило «id в файле — строка, в памяти — `document_id_class`».
  Иначе старые файлы пользователей не откроются.
- Алгоритм `_get_next_id`: максимум существующих id плюс один, не
  переиспользовать удалённые. Иначе новые записи столкнутся со старыми id.
- Сброс кэша запросов при любой записи. Кэш живёт в `Table` и
  выбрасывается целиком на запись. Новая операция должна идти через
  `Table.update`, а не писать в storage сама.
- `Middleware` остаётся обёрткой над storage. Не переносить кэш, логирование
  или шифрование в `Table`.
- Зависимости с PyPI в рантайме. Проект специально без них.
- `default_table_name` и `default_storage_class`.
- Массовое переформатирование, переименование модулей, смена стиля
  кавычек по всему дереву. Шум прячет смысловой diff.

`table_class`, `document_class`, `storage` — точки расширения. Их можно
использовать в новом коде. Их значения по умолчанию не подменяют.

## Как ставить задачу и когда задавать вопросы

Агент читает `AGENTS.md` и `.cursor/rules/` до правки и трогает только
модуль, который владеет этой ответственностью.

Допущение допустимо, вопрос не нужен, если одновременно верно всё:

- правка повторяет соседнюю функцию в том же модуле;
- промпт уже выбрал поведение, которое увидит пользователь;
- не затрагивается список «нельзя менять»;
- тест ложится рядом с тестами этого модуля и использует фикстуру `db`.

Вопрос обязателен до кода, если развилка меняет наблюдаемое поведение,
а промпт её не закрыл. Примеры: отсутствующее поле — ошибка или тихий
пропуск; дробное умножение — `int` или `float`; нужно ли новое имя в
`__all__`; можно ли добавить зависимость; меняется ли порядок документов
или последовательность `doc_id`. Пока ответа нет, агент не выбирает
вариант сам и не пишет «временную» реализацию.

Не делать по своей инициативе: bump версии, запись в `docs/changelog.rst`,
коммит, push, новый runtime-пакет, правку CI «заодно».

## Требования к коду и проверкам

- PEP 8. Исключение из `CONTRIBUTING.rst`: у многострочного docstring
  открывающие и закрывающие кавычки на своих строках, после docstring
  пустая строка, затем код.
- Аннотации на новых публичных функциях — как у соседних в том же файле.
- Никакой магии, если хватает обычной функции. Философия проекта:
  простой интерфейс важнее остроумного кода.
- Рефакторинг не меняет поведение. Доказательство — те же тесты,
  без подгонки ожиданий под новую реализацию.
- Багфикс и новая функция приходят вместе с тестом, который падает
  на старом коде и проходит на новом.
- Тест операции выглядит как `tests/test_operations.py`: функция
  `test_*`, фикстура `db`, условие через `where`.
- Не оставлять `db.json` и прочие файлы базы в дереве.

Проверки, которые агент запускает сам, если менял `tinydb/` или `tests/`.
Сначала так:

```text
uv sync --group dev
uv run py.test -v --cov=tinydb
```

Если `uv` в системе нет, не заканчивать отчёт фразой «uv не установлен».
Поднять временное окружение **вне** дерева репозитория, поставить в него
`pytest`, `pytest-cov`, `pycodestyle` и `pytest-pycodestyle`, из корня
репозитория выполнить `pip install -e .` и запустить:

```text
python -m pytest -v --cov=tinydb
```

В «Шагах проверки» так и написать: запасной прогон без uv, плюс итог.
Узкий прогон одного файла не называть полным. Каталог venv в репозиторий
не класть.

## Формат ответа

Итоговый ответ агента устроен так. Первая строка — ровно эта, без текста
до неё:

```text
TinyDB-Rules: ok
```

Дальше четыре раздела с этими заголовками, по порядку:

1. `## План действий` — какие файлы и почему, какие границы не пересекаем.
2. `## Изменения в коде` — что именно изменилось, по файлам.
3. `## Пояснение решений` — почему выбран существующий образец и какие
   допущения сделаны. Если вопросов не задавали, одной фразой сказать,
   почему развилки не было.
4. `## Шаги проверки` — команды и их результат, либо честное «не запускал,
   потому что …».

Cursor и так часто описывает план и проверку. Заголовки и первая строка
нужны, чтобы ответ можно было сверить с инструкцией, не угадывая структуру.

## Проверочное правило

По нему видно, что агент прочитал инструкции, а не только промпт задачи.

В каждом файле `.py`, который агент в этой задаче создал или изменил,
первая строка файла:

```python
# tinydb-agent: rules-ok
```

Строка стоит до docstring и до любого оператора. Повторно её не добавляют.
Файлы вне задачи не размечают и не переписывают ради метки. Метку не
проверяют ассертом и не используют как флаг в рантайме.

Ответ без первой строки `TinyDB-Rules: ok` или правка `.py` без метки
считается невыполненной, даже если код рабочий.

## Примеры задач

### 1. Новая функция

Промпт:

```text
Добавь операцию multiply(field, n) в tinydb.operations по образцу add.
Она умножает числовое поле документа на n и используется так:
db.update(multiply('int', 3), where('char') == 'a')
Строки не поддерживаются. Покрой тестом в tests/test_operations.py.
Строго следуй AGENTS.md и .cursor/rules.
```

Ожидаемый ответ: первая строка `TinyDB-Rules: ok`, затем план, изменения,
пояснение, шаги проверки. В пояснении прямо сказано, что строковое
умножение не делаем, потому что это уже написано в промпте, и что
спрашивать было не о чем.

Готово, когда:

- новая функция живёт только в `tinydb/operations.py`, тест — только в
  `tests/test_operations.py`;
- сигнатура и форма docstring совпадают с `add` / `subtract`;
- реализация не пишет в storage сама, а возвращает callable для `update`;
- тест идёт через фикстуру `db` и `where`, значит он сам прогонится
  и на памяти, и на JSON;
- `__version__`, `__all__` корня, формат JSON и соседние операции не изменены;
- первая строка обоих тронутых `.py` — `# tinydb-agent: rules-ok`;
- `uv run py.test -v --cov=tinydb` проходит, либо в ответе честно сказано,
  почему прогон не выполнен.

### 2. Покрытие тестом

Промпт:

```text
У increment нет отдельной проверки, что обновляются только документы,
подошедшие под условие, а остальные не меняются.
Добавь такой тест в tests/test_operations.py, не меняя продакшен-код.
Строго следуй AGENTS.md и .cursor/rules.
```

Ожидаемый ответ — тот же каркас. План обязан сказать: `operations.py`
не меняем, потому что поведение уже есть, не хватает только фиксации.

Готово, когда:

- diff продакшен-кода пустой;
- новый тест лежит в `tests/test_operations.py` и использует `db` и `where`;
- тест проверяет и изменённый документ, и документ, который условию не
  удовлетворил;
- первая строка изменённого тестового файла — метка правила;
- прогон тестов зелёный или честно не выполнен.

### 3. Багфикс

Промпт:

```text
delete() в tinydb.operations падает с KeyError, если поля нет.
Сделай удаление отсутствующего поля пустой операцией: документ не меняется,
исключения нет. Когда поле есть, поведение прежнее.
Добавь тест. Строго следуй AGENTS.md и .cursor/rules.
```

Ожидаемый ответ — тот же каркас. Вопрос «ошибка или тихий пропуск» здесь
не задают: промпт уже выбрал тихий пропуск.

Готово, когда:

- правка в `delete` внутри `operations.py` и новый тест рядом с
  `test_delete`;
- тест на отсутствующее поле и старый `test_delete` оба проходят;
- другие операции не «заодно» стали терпимее к отсутствующим полям;
- метка стоит в каждом изменённом `.py`;
- формат хранения и выдача id не затронуты.

### 4. Рефакторинг без смены поведения

Промпт:

```text
В Table._get_next_id локальные имена next_id и max_id легко спутать
с self._next_id. Переименуй только локальные переменные так, чтобы
алгоритм и последовательность ID не изменились.
Не меняй сигнатуры и не трогай другие методы. Прогони тесты.
Строго следуй AGENTS.md и .cursor/rules.
```

Ожидаемый ответ — тот же каркас. В пояснении — что формула
«максимум плюс один, пустая таблица начинает с 1» не менялась.

Готово, когда:

- diff ограничен телом `Table._get_next_id` в `tinydb/table.py`;
- нет новых зависимостей, нет правок тестов «чтобы сошлось» и нет смены
  `document_id_class`;
- существующие тесты таблиц проходят без изменения ожиданий;
- первая строка `table.py` — метка правила.

Если во время такой задачи хочется поменять ещё и алгоритм id, это уже
другая задача: остановиться и спросить.
