# Отчёт: AI-инструкции для TinyDB

История работы, а не сводка. Ниже — что выбирал, какие промпты отправлял, где ошибся сам и где агент упёрся в дыру в инструкциях.

## Инструмент

Инструкции заточены под **Cursor Agent** в IDE Cursor.

Cursor сам подхватывает два вида проектных документов (документация: <https://cursor.com/docs/rules>):

- `AGENTS.md` в корне — обычный Markdown без frontmatter. Его читает Cursor и другие агенты, которые понимают этот файл. Это канонический текст: контекст, границы, стиль, формат ответа, примеры задач.
- `.cursor/rules/*.mdc` — Project Rules. У файла YAML-frontmatter (`description`, `globs`, `alwaysApply`). Cursor подмешивает правило в контекст всегда, по маске файлов или когда описание совпадает с задачей. Обычный `.md` в этой папке Cursor игнорирует. Файл `.cursorrules` не использовал: для Cursor это устаревший формат.

Правила разложены по одному вопросу, как просит документация Cursor:

| Файл | Когда попадает в контекст | О чём |
| --- | --- | --- |
| `.cursor/rules/00-marker-and-reply.mdc` | всегда | первая строка ответа и метка в изменённых `.py` |
| `.cursor/rules/01-context.mdc` | всегда | что это за библиотека, модули, как гонять тесты |
| `.cursor/rules/02-boundaries.mdc` | всегда | что нельзя менять и когда надо спросить |
| `.cursor/rules/03-python-style.mdc` | открыты `tinydb/**/*.py` или `tests/**/*.py` | PEP 8, образец операции, тесты |
| `.cursor/rules/04-task-examples.mdc` | агент сам подтягивает по описанию | границы четырёх типовых задач, полный текст в `AGENTS.md` |

Проверку делал тем же классом агента: локальный агент Cursor в этой рабочей копии. Ему не вставлял текст правил в промпт. Просил прочитать `AGENTS.md` и `.cursor/rules` и строго их соблюсти.

Проверочное правило, по которому видно, что инструкции прочитаны:

- первая строка ответа — ровно `TinyDB-Rules: ok`;
- первая строка каждого `.py`, который агент создал или изменил, — `# tinydb-agent: rules-ok`.

Метка в файле важнее строки в чате: она остаётся в diff. Короткая карточка-саммари, которую Cursor показывает над ответом, эту строку не сохраняет. На это нельзя опираться.

## Что взял за проект

Репозиторий задания `https://github.com/sasha1343p-hash/DZ3` был пустым: только `git init`, ветка `main`, remote `origin`, коммитов не было. Кладём сюда снимок [TinyDB](https://github.com/msiemens/tinydb) **4.9.0** и инструкции. В upstream pull request не открывал: проект в режиме сопровождения, а учебные правила автору библиотеки не нужны.

TinyDB — документная база на чистом Python, без зависимостей и без сервера. Документ — `dict`, по умолчанию один JSON-файл. Публичный фасад маленький (`TinyDB`, `Query`, `where`, `Storage`, `JSONStorage`), запись идёт через `Table`, операции для `update` лежат отдельно в `operations.py` и сами файл не открывают. Этого хватает, чтобы поймать агента, который «заодно» переписывает формат JSON или алгоритм `doc_id`.

## Неудачные попытки до живого агента

### 1. Клонирование прямо в папку задания

Команда:

```text
git clone --depth 1 https://github.com/msiemens/tinydb.git .
```

Ответ git:

```text
fatal: destination path '.' already exists and is not an empty directory.
```

Папка выглядела пустой, но в ней уже был `.git` с remote на `sasha1343p-hash/DZ3`. Клонировать поверх этого remote нельзя: потерялся бы адрес, куда сдавать PR.

Как починил: клонировал TinyDB во временный каталог и скопировал файлы в задание через `robocopy`, исключив чужой `.git`. Свой remote остался. Снимок 4.9.0 закоммитил на `main` отдельно, чтобы в PR было видно инструкции, а не всю библиотеку как одну кашу.

### 2. В черновике правила лежало готовое решение

В первой версии `.cursor/rules/03-python-style.mdc` «хороший» пример был не существующий `add`, а уже написанная функция `multiply` с телом `doc[field] *= n`. Правило с `globs` на `tinydb/**/*.py` как раз подгружается, когда агент редактирует операции. Проверка «придумай multiply по образцу add» превратилась бы в «скопируй код из правила».

Это не запуск агента, но это дыра, которую я сам же и проделал. До первого прогона пример заменил на уже существующий `add`. В `AGENTS.md` сценарий `multiply` остался промптом и критериями готовности, без тела функции.

### 3. Пример в AGENTS.md не компилировался бы

В сценарии «подменить хранилище» в сниппете стоял `JSONStorage`, а импорт был только у `MemoryStorage`. Абзац ниже честно писал, что `JSONStorage` надо импортировать из `tinydb.storages`, но сам пример этому противоречил. Поправил импорт в сниппете до запуска агента. Иначе агент мог бы воспроизвести нерабочий пример в новом коде.

### 4. GitHub CLI не был установлен и не залогинен

`gh` в PowerShell не находился (`CommandNotFoundException`). Поставил `GitHub.cli` 2.103.3 через winget. После установки `gh auth status` ответил: `You are not logged into any GitHub hosts`. К PR это вернулось в конце, см. раздел про трудности. На написание инструкций не повлияло.

В `AGENTS.md`, в `01-context.mdc` и в `03-python-style.mdc` заменил «если uv нет — так и напиши» на обязательный запасной прогон: venv вне дерева, те же четыре пакета, `pip install -e .`, `python -m pytest -v --cov=tinydb`. Повторно гонять `multiply` не стал: функция уже в дереве, второй агент начал бы дублировать её.

## Трудности

- Учебный репозиторий и исходники TinyDB нельзя было склеить вторым `git clone` в ту же папку. Remote задания важнее, чем история коммитов upstream, поэтому в `main` лежит снимок файлов 4.9.0 одним коммитом, без истории автора.
- `uv` в окружении нет, хотя именно им запускает тесты CI TinyDB (`uv sync --group dev`). Extra `[dev]` в `pyproject.toml` тоже нет, `pip install -e ".[dev]"` не ставит pytest. Пока инструкция этого не произнесла, агент законно остановился.
- `gh` после установки не авторизован. Push и PR зависят от того, есть ли у git credential manager доступ к `github.com` под аккаунтом `sasha1343p-hash`. Если PR в конце отчёта нет, причина здесь, а не в инструкциях.
- Проверочная фраза в чате и проверочная строка в файле ведут себя по-разному. В правиле оставил обе: строка в файле видна проверяющему в diff, строка в ответе видна в переписке.
